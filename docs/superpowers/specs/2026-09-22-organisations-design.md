# Organisations

**Date:** 2026-09-22
**Status:** Approved (design sections reviewed in conversation)

## Problem

StudioManager assumes one business per install. The user runs two: a design
studio and a music label. Today the only way to keep them apart is a second
copy of the app, which duplicates preferences, the updater and the Dock icon,
and still shares one application-support folder.

An organisation is a fully separate set of business data inside one app:
clients, projects, tasks, time, calendar events, wiki, resources, quotes,
invoices, expenses, income, finances, business profile, bank details,
activities, expense categories, templates, invoice PDFs and receipts. The app
shows one organisation at a time and switches between them in place.

## Decisions taken with the user

| Question | Decision |
|---|---|
| What is separate | All data. App look-and-feel preferences shared; a small set of business preferences per organisation (section 4). |
| Switching | Switcher in the sidebar, same window, in-place swap. No multi-window, no launch-time chooser. |
| New organisation | Dialog offers "Start empty" or "Start from the current organisation's settings". |
| Cross-organisation views | None. Every page shows the active organisation only. |
| Architecture | A: folder per organisation with a registry file (see Alternatives). |

## Current mechanics this builds on

- Rust holds `ActiveDb(Mutex<String>)`, the active database filename; the
  frontend opens `sqlite:<name>`, which the SQL plugin resolves against the
  app config folder (same as the app data folder on macOS).
- Test mode and presentation mode copy the production file, switch the name,
  close and reopen the frontend connection, clear the query cache and reload.
- Invoice PDFs and receipts are written to `<app data>/invoices` and
  `<app data>/receipts`; rows store absolute paths. A healing statement in
  `ensureSchema` already rewrites stored paths after the bundle rename.
- Plugin migrations are registered for `sqlite:studiomanager.db` only. Every
  other database gets its schema by being a copy of production. The frontend
  `ensureSchema` step applies everything added since migration 006 on open.
- Preferences live in localStorage keys read by the app store.

## Design

### 1. Data layout

```
<app data>/
  organisations.json
  orgs/<id>/studiomanager.db            (+ -wal / -shm)
  orgs/<id>/invoices/
  orgs/<id>/receipts/
  orgs/<id>/studiomanager_test.db        (while test mode is on)
  orgs/<id>/studiomanager_presentation.db (while presentation mode is on)
  orgs/<id>/studiomanager_snapshot.db    (test-mode snapshot)
```

`organisations.json`:

```json
{
  "version": 1,
  "activeId": "k3f9a2",
  "organisations": [
    {
      "id": "k3f9a2",
      "name": "Studio",
      "createdAt": "2026-09-22T10:00:00Z",
      "prefs": {
        "showIncome": true,
        "showTasksPage": true,
        "showTimeOverview": true,
        "calendarSync": false,
        "calendarName": "StudioManager",
        "backupPath": "/Users/…/Compta/AppBackups",
        "exportLanguage": "FR"
      }
    }
  ]
}
```

Ids are six lowercase base-36 characters generated by Rust. Order in the
array is display order. Rust owns the file: the frontend reads and writes it
only through commands, and writes are whole-file atomic (write to a temp
file, rename).

### 2. Upgrade from the single-database layout

Runs once, in Rust, at startup, before the frontend opens any database, when
`organisations.json` does not exist and `studiomanager.db` exists at the root.

1. Write `studiomanager_upgrade_snapshot.db` from the production database
   using the existing online-backup snapshot helper.
2. Count rows in `invoices` and `expenses`, and count files in `invoices/`
   and `receipts/`.
3. Create `orgs/<id>/`.
4. Rename, in order: `studiomanager.db`, `studiomanager.db-wal`,
   `studiomanager.db-shm` (if present), `invoices/`, `receipts/`. Renames
   stay on the same volume, so each is atomic. Companion files of test,
   presentation and snapshot databases at the root are deleted, never moved:
   they are disposable copies.
5. Rewrite stored paths in one transaction:
   `UPDATE expenses SET receipt_path = REPLACE(receipt_path, '/ch.studiomanager.app/receipts/', '/ch.studiomanager.app/orgs/<id>/receipts/')`
   and the same for `invoices.pdf_path` with `invoices/`. Rows whose path
   does not contain the app folder (external files) are untouched.
6. Re-count. Any mismatch, or any error in steps 3 to 5, triggers rollback:
   reverse the renames that succeeded, remove the empty `orgs/<id>/`, and
   return an error. The app then starts on the legacy layout, shows the
   error in the existing fatal overlay with the snapshot path, and does not
   retry until the next launch.
7. Write `organisations.json` with one organisation named after
   `business_profile.owner_name` (fallback "Studio"), `activeId` set, and
   `prefs: null`. Rust cannot read localStorage, so the frontend fills the
   prefs on its first load (section 4) and the null marks that it still has
   to. The snapshot is deleted on the next successful launch.

Backups in external folders are not touched. Release notes recommend a
manual Backup Now before updating.

### 3. Rust side

`ActiveDb` becomes:

```rust
struct ActiveOrg { id: String, dir: PathBuf }   // dir = <app data>/orgs/<id>
```

with helpers `db_path(name)` and `docs_dir(kind)`. Every command that builds
a path from the app data folder (execute_batch, test mode, presentation mode,
snapshot, restore, has_snapshot, get_active_db) reads from `ActiveOrg`, so
they operate on the active organisation without other changes.

New commands:

| Command | Behaviour |
|---|---|
| `list_organisations` | Returns the registry. |
| `create_organisation(name, seed_from_current: bool, prefs)` | Creates the folder and an empty database with the full schema (migration runner). If `seed_from_current`, copies rows of `business_profile`, `activities`, `expense_categories`, `invoice_templates`, `workload_templates` from the active database. Appends to the registry, does not switch. |
| `rename_organisation(id, name)` | Registry only. |
| `reorder_organisations(ids)` | Registry only. |
| `delete_organisation(id)` | Refused for the active organisation and for the last one. Moves `orgs/<id>/` to the Trash (`trash` crate) and removes it from the registry. |
| `switch_organisation(id)` | Sets `ActiveOrg`, persists `activeId`. Refused while test or presentation mode is on (frontend exits the mode first). |
| `get_organisation_prefs(id)` / `set_organisation_prefs(id, prefs)` | Registry read/write. |

Migration runner: `migrate_db(path)` applies the six SQL files from
`src-tauri/migrations` in order, tracking progress in a `schema_migrations`
table (`version INTEGER PRIMARY KEY, applied_at`). On a database that has
the plugin's `_sqlx_migrations` table but no `schema_migrations`, it seeds
its table from the plugin's highest version before applying anything. It is
called by `create_organisation`, by the upgrade step, and by
`switch_organisation` and startup for the active organisation, so a
database that is ever behind catches up. `add_migrations` is removed from
the plugin builder. The frontend `ensureSchema` keeps running on every open.
Future schema changes are added as numbered files and applied by the runner.

Presentation and test mode: unchanged logic, paths from `ActiveOrg`. The
snapshot used by test mode lives inside the organisation folder.

### 4. Frontend: organisation store and switching

New `org-store` (zustand): `organisations`, `activeId`, `activePrefs`,
loaded from `list_organisations` at startup before the router renders.
The database module reads the active organisation's database URL
(`sqlite:orgs/<id>/<name>`) from the store instead of a fixed name; the
existing `currentDbName` logic for test and presentation mode becomes a
suffix on top of that.

A `orgPaths()` helper replaces the five inline `appDataDir() + "/invoices"`
and `"/receipts"` constructions (invoicePdfStore, ExpensesPage, IncomePage,
QuotesPage, InvoicesPage, backup restore) and returns the active
organisation's folders.

`switchOrganisation(id)` sequence:

1. `confirmIfDirty()`; abort if declined.
2. If test or presentation mode is on, exit it (existing handlers).
3. Stop the active timer if it belongs to this organisation and log its
   time; the timer key in localStorage is namespaced by organisation id.
4. Close the database connection (`switchDb` path).
5. `invoke("switch_organisation")`.
6. `queryClient.clear()`; close all tabs; reset list UI state that refers to
   rows (sort keys stay, they are column names).
7. Load `activePrefs` into the app store.
8. Navigate to `/`. The recurring check and the overdue check run once, as
   after launch.

localStorage keys namespaced by organisation id: `open-tabs`, `activeTimer`,
`tasksCollapsedProjects`, `tasksProjectOrder`, `lastAutoBackup`. All other
keys stay global.

Per-organisation preferences (registry `prefs`): `showIncome`,
`showTasksPage`, `showTimeOverview`, `calendarSync`, `calendarName`,
`backupPath`, `exportLanguage`. The app store exposes them as today; setters
write through to `set_organisation_prefs`. When the store loads an
organisation whose `prefs` is null (only ever the one created by the
upgrade), it builds them from the current localStorage values, writes them
through, and removes those keys from localStorage. New organisations get
defaults (income shown, tasks page shown, time overview shown, sync off,
calendar name "StudioManager", no backup path, export language FR).

App-wide (unchanged, localStorage): theme, accent, dark mode, app language,
date format, reduce motion, native notifications, sidebar collapsed, project
open mode, `maxBackups`, `autoBackupInterval`, `backupPath2`, calendar view,
peek width, per-page sort keys.

### 5. User interface

- **Switcher** at the top of the sidebar, under the wordmark: the active
  organisation's name with a chevron; the collapsed sidebar shows the first
  letter in a small tile. Opens a menu: organisations with a check mark on
  the active one, a divider, "New organisation…", "Manage organisations…"
  (opens Settings → Organisations). Shortcut Cmd+Shift+O. Keyboard
  navigable like the sidebar.
- **Window title**: `StudioManager — <name>`.
- **Create dialog** (Modal): name (required, unique, trimmed), radio
  "Start empty" / "Start from the current organisation's settings" with a
  one-line description of what is copied. Create switches to the new
  organisation immediately and shows a toast.
- **Settings → Data → Organisations** card: list with rename inline,
  drag-to-reorder, delete. Delete asks to type the name, is disabled for the
  active organisation ("switch to another organisation first") and for the
  last one, and explains that the folder goes to the Trash.
- **Mode banners** (test, presentation) include the organisation name.
- **First launch after upgrade**: no dialog; the organisation exists with
  the owner's name and can be renamed in Settings.
- i18n: all new strings in `src/i18n/ui.ts`, EN and FR, FR accent-free per
  the existing parity rule.

### 6. Backups, calendar, exports, other subsystems

- **Backups**: per organisation. The backup folder name gains the
  organisation id (`backup-<id>-<timestamp>`) so two organisations sharing
  a parent folder never collide; rotation counts per organisation. Restore
  acts on the active organisation. `useAutoBackup` reads the active
  organisation's `backupPath` and `lastAutoBackup`.
- **Trustee export**: per organisation, unchanged.
- **Calendar sync**: uses the organisation's `calendarName`; events created
  by one organisation carry ids stored in that organisation's database, so
  deletion and update stay scoped.
- **Recurring invoices, overdue detection, notifications**: run against the
  active database; they re-run after a switch. In-app notifications live in
  the database, so they are per organisation.
- **Updater, window state, native notifications**: app-wide.

### 7. Testing

- Rust: migration runner on a fresh file and on a plugin-migrated fixture;
  upgrade step on a fixture folder mirroring the legacy layout (files,
  companion files, rows with app-folder and external paths), including a
  forced failure after the first rename to verify rollback; create with and
  without seeding; delete guards.
- Frontend (vitest): org store load and switch sequence order (dirty guard
  first, mode exit, close, invoke, cache clear, tabs, prefs, navigate);
  preference split (per-org setter writes through, global setter does not);
  `orgPaths()` used by every document writer; switcher menu and create
  dialog; namespaced localStorage keys.
- Rehearsal before release: run the upgrade against a copy of the user's
  real application-support folder in a scratch location; compare every
  table's row count and every document file's checksum before and after;
  open the result in a dev build.
- Manual: switch with a dirty form, with a running timer, inside test mode,
  inside presentation mode; backup then restore after a switch; calendar
  sync from two organisations.

## Alternatives considered

- **One database, organisation column on every table**: every query, hook,
  PDF and export would need a filter, and one missed filter leaks data
  between organisations. Rejected.
- **Separate app instances via launch profiles**: closest to "duplicates of
  the app" but no in-app switching, two Dock icons, duplicated preferences
  and updater. Rejected by the switching decision.

## Out of scope

Cross-organisation dashboards or totals; moving a client or project between
organisations; sharing clients; per-organisation themes; multi-window.

## Risks

- The upgrade moves the user's only data. Mitigated by snapshot, atomic
  renames, count verification, rollback, and the real-data rehearsal.
- Removing plugin migrations changes how schema changes ship. Mitigated by
  the runner recognising plugin-migrated databases and by tests on both
  fixture kinds.
- Absolute document paths remain absolute. Acceptable now; a later change to
  relative paths would be a small follow-up on top of `orgPaths()`.
