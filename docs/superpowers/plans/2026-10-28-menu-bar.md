# Menu Bar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A StudioManager menu bar icon, shipped in the app, with an Agents tab (live list + answering prompts), a Usage tab (plan limits with pacing and alerts, tokens, agent time) and a Day tab (user-defined routines: agent prompts or commands, optional schedule), so AgentBar can be retired.

**Architecture:** Everything runs in the StudioManager process. Rust gains a tray icon and a second, borderless webview window (`menubar`) that renders a `/menubar` route; app lifetime changes (keep running when the main window closes, start at login). New Rust modules beside the Agents engine compute usage (status-line limits written by a new `--statusline` mode of the bundled `studiomanager-mcp` sidecar, plus a transcript scan) and run routines on a schedule. The panel reuses the Agents page components and the app's UI kit.

**Tech Stack:** Tauri 2 (new: `tray-icon` feature, `tauri-plugin-autostart`), Rust, React 19 + TS + Tailwind 4, recharts (already a dependency), Vitest.

**Spec:** [2026-10-28-menu-bar-design.md](../specs/2026-10-28-menu-bar-design.md) · Builds on: [Agents window plan](2026-10-28-agents-window.md) · Reference behaviour: `~/Documents/GitHub/agent-bar/Sources/AgentBar/` (`Bar.swift`, `MenuView.swift`, `StatusLineCapture.swift`, `UsageStore.swift`, `UsageTab.swift`, `Pacing.swift`, `Activity.swift`, `SavedTasksScheduler.swift`, `DayTab.swift`).

## Global Constraints

- Reuse first ([DESIGN-SYSTEM.md](../../../DESIGN-SYSTEM.md) "Reuse First"): `PANEL_TOP_BAR`, `TabItem`, `BottomBar`, `Badge`, `Button`, `dot`, `EmptyState`, `Input`, `FormField`, `Toggle`, `SettingsCard`/`SettingRow`, `ContextMenu`, the Agents page's `AgentList`/`PromptAnswer`/`ModelMenu`, recharts. Anything new is named in the task report.
- One engine: the panel reads the same Rust state/commands/events as the Agents page; no second poller of `claude agents`.
- Settings: `<app data>/agents.json` gains `menuBar: bool` (default false; enabling requires `enabled`) and `limitAlerts: bool` (default true).
- Close the main window → app keeps running with the icon (only when `menuBar` is on). ⌘Q quits. At login: started with `--menubar`, the main window stays hidden. Dock reopen shows the window.
- Icon: StudioManager's arrow (`Icon/StudioManager.icon/Assets/SM-Arrow.svg`) as a template image; amber `#d97706` while any agent is in Needs you.
- Panel: borderless, 340 px wide, under the icon, closes on blur. Tabs: Agents, Usage, Day.
- Alerts (as AgentBar): one notification when a window passes **80%**; one **pace alert** when projected 100% is more than **1 h** before reset; each at most once per window (key: window name + `resets_at`); off when `limitAlerts` is false (still recorded, no backlog when turned back on).
- Pacing: wall-clock projection from the earliest sample of the current window, idle time included (AgentBar `Pacing.swift`). Meters amber from 75%, red from 90%.
- Tokens = output + fresh input (cache reads excluded), last 7 days, grouped by client through linked folders (`FolderIndex`), plus the week's model mix ("Mostly Opus 5.5 92%, Sonnet 5.5 8%" / "All Opus 5.5" at ≥ 99%).
- Agent time: per client and project, Today / Week, a guide ("A guide from agent activity, not a timesheet"), "Copy as text". Never written to time entries.
- Status line: StudioManager's command is `<bundle>/Contents/MacOS/studiomanager-mcp --statusline`; it reads stdin, keeps `rate_limits` (either a `limits` list or named windows `five_hour`/`seven_day`/`seven_day_<model>`), writes `<app data>/limits.json` and appends `<app data>/limits-history.jsonl`, prints nothing. Setup only after a preview; back up `~/.claude/settings.json` first; remember the previous `statusLine` value to restore. A different existing `statusLine` is replaced only after a warning the user confirms.
- Routines: kinds `agent` (folder, model, name, prompt text or prompt file) and `command` (program, args, cwd; argv only, never a shell); a prompt file becomes the task "Read and follow the instructions in <path>." so the 8000-char task limit never bites; status of a command = last non-empty output line, exit code 0 = done; schedule = `HH:MM` + `daily | weekdays`; catch up on start/wake if < 2 h late; at most one scheduled run per routine per day; a failed scheduled run posts one notification. Stored in `<app data>/routines.json` and `<app data>/routine-runs.json`. Only routines the user created run; the webview passes routine ids, never programs or arguments.
- No network port. EN + FR copy in `src/i18n/ui.ts`. No personal content (Art Basel, briefs) in code or fixtures; the repo is public.
- Checks before each commit: `npx tsc --noEmit`, `npx vitest run`, `npm run lint`, `cargo test` in `src-tauri` (and `src-tauri/mcp` for Task 4), clippy without new warnings. Prefix commands with `env PATH=/Users/loris.briguet/.nvm/versions/node/v22.22.0/bin:/Users/loris.briguet/.cargo/bin:/usr/bin:/bin`; `CARGO_TARGET_DIR=/Users/loris.briguet/cargo-target-studiomanager` (mcp: `…-mcp`).

## Review Focus

1. **The main window closed while the panel answers a prompt or a routine runs:** nothing may depend on the main window's webview (alerts, scheduling and notifications run in Rust) → Task 6/10 tests drive the logic without a window.
2. **Claude's `settings.json` changed between preview and write, or is not valid JSON:** write nothing, say so (Task 5 test `status_line_install_refuses_when_settings_changed`).
3. **Mac asleep across a scheduled time, or the app started late:** run once if < 2 h late, never twice the same day, never for a past day (Task 10 test `catch_up_rules`).
4. **A command routine that never ends or floods output:** a timeout (10 min) kills it and marks it failed; only the last 64 KB of output is kept (Task 9 test `command_timeout_and_tail`).
5. **Status-line history growing forever / a second capture process writing at the same time:** append whole lines in one write, trim to 8 days at most once an hour (Task 4 test `history_append_and_trim`).
